# BirdBuddy API Functional Test Scenarios

## Test approach and notation

- Execute destructive and rate-limit tests in a controlled QA tenant unless a scenario explicitly says otherwise.
- Use unique, run-scoped names and UUIDs so tests can run repeatedly and in parallel.
- A **read key** has `birds:read` only; a **write key** has `birds:write` and its implied `birds:read`; a **no-scope key** is valid but has neither bird permission.
- A **canonical Bird assertion** verifies all 12 fields (`uuid`, `name`, `scientificName`, `description`, `primaryColor`, `secondaryColor`, `flightPattern`, `size`, `song`, `area`, `time`, and `migratory`), their JSON types, and their documented constraints.
- A **standard Error assertion** verifies a JSON object containing string `error` and numeric `statusCode` equal to the HTTP status; if present, `details` is an array of strings and `requestId` is a string.
- Parameterized scenarios are one scenario with a separately reported iteration for every value or case listed. A failed iteration fails the scenario.
